# SB-08 — Prototype acceptance and handoff

## Objective

Run the approved P01–P14 acceptance checks on the integrated prototype and produce a reproducible evidence-backed handoff with remaining MVP limits.

## Requirements

Read [Prototype specification](../requirements/cost_calculator_handover/DESKTOP_PROTOTYPE_SPEC.md) and [application specification](../requirements/cost_calculator_handover/APP_SPECIFICATION.md). The application specification overrides compatible workbook formulas; proposals are not approved behavior. The original technical implementation plan is background evidence; package boundaries and current-code corrections in these briefs govern execution. P01–P14 are approved criteria, not assumed passes. The declared Mac one-second response target and ±0.1% geometry tolerance must be measured independently of arithmetic assertions.

## Dependencies

Depends on: SB-07

Dependencies mean integrated predecessor work, including transitive predecessors, not a concurrent agent’s promise or an unreviewed artifact.

## Scope

- Verify clean service provisioning/migration/seeding and documented startup from integrated commits. Record target OS/architecture/CPU/GPU/RAM and client/service/calculator/schema builds.
- Run every approved criterion with the original analytic fixtures, real persistent backend, source hashes, input/output captures and native evidence.
- Inject unavailable/rejected/lost-response backend writes and stale completions; verify current-session unsaved edit retention, explicit retry and no duplicate records.
- During controlled five-second analysis and service delays measure actual navigation/selection response, requiring at most one second. Keep timing evidence separate from deterministic tests.
- Check immutable source across all declared entry paths, exact measurement usage, historical result preservation and honest prototype labels.
- Record defects for their owning packages and rerun affected acceptance after integrated corrections. Do not implement full MVP or silently waive failed criteria.

## Interfaces

Use the released version 1 commands/contracts and package handoffs as the test interface. Publish an acceptance matrix with criterion, fixture, build/contract versions, steps, expected/actual values, pass/fail, evidence location and unresolved issue. Include source hashes and immutable calculation IDs so results can be reproduced. Handoff documentation describes service configuration without credentials.

## Ownership

Own `docs/solidbom-prototype.md` and package-specific acceptance records/evidence index under `docs/solidbom/execution/`, with exact filenames reserved by the coordinator. SB-00 retains ownership of shared execution ledgers/bootstrap files. Corrections to implementation go to the owning package or an explicit coordinator reservation. Native screenshots/recordings remain under `.context/` unless an approved public-safe artifact process says otherwise. Work in the dedicated user-created Conductor workspace assigned to this package. Do not rename its branch without an explicit request. Only one package owns a shared file at a time; ask the coordinator to reserve an integration edit before changing an unlisted shared file. SB-00 owns shared execution/bootstrap documents. Never modify generated files. Run `cargo xtask ci` before every commit; do not treat a package-specific check as a substitute. Do not claim unrun tests passed.

## Acceptance

- Every P01–P14 row has actual evidence or is explicitly failed/blocked/unrun; no inferred pass from unit tests alone.
- Fresh persistent setup and complete desktop-process close/reopen preserve source, associations and saved calculations.
- Record actual P13 maximum response and machine details; verify arithmetic independently with the approved money tolerance and geometry with ±0.1%.
- Run root formatting, appropriate clippy/tests and `cargo xtask ci`; separately run service formatting/clippy/integration tests for its independent workspace.
- Completion requires all approved checks passing or a clearly reported incomplete handoff; never represent remaining failures as acceptance. Full tube recognition/customer-file accuracy, production deployment and full MVP remain outside the claim.

## Assignment gate

SB-07 and the complete transitive package chain must be integrated. Assignment lists exact release/build commits, contract versions, fixture hashes and predecessor evidence. The declared test Mac, native display and isolated persistent service/database must be available; otherwise report the blocked acceptance prerequisites.

## Handoff

Deliver acceptance matrix, reproduction/startup instructions, test outputs, native evidence references, exact integrated builds and all remaining failures/MVP gaps. State whether the prototype satisfies P01–P14, distinguishing software acceptance from deferred production/customer-geometry readiness. Do not publish, push or rename branches without the session’s required authorization.
