## Contract changes and follow-up

Proposed by this ticket, version 1, additive to API version 2; the coordinator lock is still open:

- Portable types in `crates/solidbom-contract/src/recognition.rs`: open category codes,
  `SuggestionEvidence`, `PredictionProvenance`, `ClassificationSuggestion`,
  `CatalogMatchSuggestion`/`CatalogMatchCandidate`, `ConfirmedCatalogReference`,
  `ProjectCatalogOverride`, `CatalogRecord` with `effective_inputs`, and `RecordSuggestions`.
- Additive: `ClassificationPrediction` provenance fields (`prediction_version`, `analysis_key`,
  `evidence`, `suggested_at`), `ReviewedPart.catalog`, `PartConfirmation.catalog` with
  `CatalogConfirmation`, `CatalogComponentVersion.attributes`, `CreateComponentVersion.attributes`
  and the two new `EngineeringFact` variants.
- Route: `POST /v2/projects/{project_id}/engineering/suggestions` returns an
  `EngineeringWriteOutcome` and appends one engineering record version. Catalog confirmation rides
  the existing bulk `confirm_parts` write.

Rules this start encodes: a prediction/pending suggestion never confirms a label and never supplies
authoritative catalog price or specification; confirmation/correction is an engineer write that does
not change source geometry; a confirmed project override retains the original catalog version and
value separately; a category is an open stable code, so an added category needs no identity/schema
redesign; evaluation reports counts and per-case errors/unsupported cases without an inferred
accuracy percentage.
