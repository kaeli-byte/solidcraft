## Isolation and database state

Each test creates its own random schema (`t_<uuid>`, `support/mod.rs: TestDb::new`) in
`solidbom_sb22_tests`, applies the real migrations in it and drops that schema in suites that call
`TestDb::cleanup`. Checked after the suite:

```text
$ psql -d solidbom_sb22_tests -Atc "select count(*) from information_schema.tables where table_schema='public'"
0
$ psql -d solidbom_sb22_tests -Atc "select count(*), max(version) from \"<one t_* schema>\"._sqlx_migrations"
13|13
```

The 13 applied migrations are `0001_initial.sql` through `0013_machine_hourly_rates.sql`; the
public schema stays empty, so no test wrote outside its private schema.

47 `t_*` schemas were still present after the run, and their distribution matches exactly the four
suites that do not call `TestDb::cleanup` in their source (`grep -c "cleanup()"` = 0):
adoption 15 `TestDb::new` + commercial 7 + engineering 16 + projects 9 = 47. The other nine suites
call cleanup once per `TestDb::new` and left nothing behind. This is pre-existing service test
harness behavior (the same four suites had it before this branch; it is not a test failure and no
test value is shared). The whole `solidbom_sb22_tests` database was dropped after the run, so
nothing from this evidence stays on the host:

