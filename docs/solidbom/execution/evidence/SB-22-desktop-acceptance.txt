3. Disposable database phases (why the database was recreated twice inside the run)
--------------------------------------------------------------------------------

One disposable database name, `solidbom_sb22_desktop`, was used throughout; it was dropped and
recreated at two phase boundaries, and no other database was touched. Reason: the desktop derives a
project id deterministically from the source SHA-256, so the same fixture cannot be imported twice
into one database, and an evidence-phase rerun must start from a clean store rather than reuse the
half-finished attempt.

| Phase | Database instance | Rows covered | Raw evidence |
|---|---|---|---|
| 1 | created 23:32:30Z | P01–P08, P13 (both halves), A06, P14 | session-A/B/C/D/H/I/A06.json, environment.json |
| 2 | created 23:38:40Z | P09, P11 | sessions/session-P09.json, session-P11.json |
| 3 | created 23:39:54Z | P10, P12, final health | sessions/session-P10.json, session-P12.json, final-health.json |

P09 evidence phase 2 was a clean rerun: the first attempt had already produced its observations and
screenshots but failed at the final JSON write; the database was recreated so the rerun could import
the fixture again. P10 evidence phase 3 was the clean rerun after a script defect (wrong variable
name at the end of the P10 script) had discarded the first attempt's JSON. Every row above is from a
real import, save, calculation and reopen against PostgreSQL; `sessions/*.json` carry the raw service
responses and database counts for the phase that produced them.

Final database state (`final-health.json`): sources 1, projects 1, project_versions 4,
calculations 3, requests 7 — the P10/P12 revisions project after recovery.
