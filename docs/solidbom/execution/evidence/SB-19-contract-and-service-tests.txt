The twelve activation domain tests cover:
- readiness is read-only and reports both selected members ready before the first accepted baseline;
- a shared sourcing/material change used by two active products refuses an A-only activation with
  `coordinated_activation_required` naming B, then a complete coordinated activation changes both in
  one project version and one accepted baseline (A activated, B re-pinned) and pins the new material;
- a shared routing change and a shared reviewed-dimension change each require the whole group;
- the three-product bypass regression: A and B share the changed part and C is independent, so a
  C-only activation is refused naming A and B, A-only is still refused naming B, the complete A+B
  activation succeeds and A can activate alone afterwards;
- a fully priced, feasible part with an unconfirmed classification is blocked until the engineer
  confirms it;
- a missing cost input (the shared part's allowance) blocks every member of the group and writes
  nothing until fixed;
- an unresolved feasibility finding blocks every member until a recorded justified exception
  resolves the disposition, and no negotiated selling price or scenario is needed;
- distinct customer revisions stay distinct part versions, the pending change on one revision's part
  requires the product that uses it even when the selected product does not, an invented revision is
  an `invalid_request` refusal and a foreign revision is a `revision_not_activatable` refusal, all
  without writing;
- only the newest draft revision appended to a product is activatable; a second delivery makes the
  older draft superseded and both readiness and activation refuse it on both routes without writing;
- stale project version, stale accepted baseline, request-id payload reuse and an injected failure
  after the project-version insert all write nothing (the injected failure plants a competing
  accepted row so the final immutable insert violates a unique constraint inside the transaction);
- the accepted history is newest-first, a historical baseline is unchanged after later edits, and an
  unknown baseline is not found;
- the readiness coordination report names the changed definition aspects and the required products.

The api route test covers `POST /activation-readiness` (200, report contents, 401, 403, 404),
`POST /activations` (201 receipt, identical retry, 409 stale project version, 403), the accepted-
baseline list and historical read (200, 404 unknown id). The stale refusal is asserted through the
version 1 error-body shape (`error.code == "conflict"` and the `stale_project_version:` message
prefix). The body-deserialization path keeps the shared axum `400` rejected-body behaviour documented
by the amended contract; the api test does not exercise that framework path.

## Fixes applied for the independent verification findings

- **B1 (blocker) pending-change coordination bypass:** the changed candidates are now compared from
  the accepted-baseline head's whole `shared_definitions` pin set through the contract's
  `pending_shared_definition_changes` helper, and every quotation-included product whose resulting
  costed structure uses a pending changed part is required in any activation, even one whose own
  members do not use it. The three-product regression is in `tests/activation.rs` and the readiness
  `coordination` report is project-wide.
- **S2 current draft:** only the newest (last) draft revision appended to a product is activatable;
  an older superseded draft is `revision_not_activatable` on both routes. The double-delivery test
  asserts the refusal writes nothing and the newest draft then activates.
- **S3 flaky test:** the two-product assertions find members by `product_id`; the activation suite
  was re-run repeatedly (five times before the helper wiring and three times on the final tree), all
  12/12, and the full service suite ran twice at 134/134.
- **S4 evidence overstatement:** the native evidence file now includes an isolated live case (project
  P3) that is fully priced and feasible with the reviewed volume confirmed and only the
  classification unconfirmed; its readiness report has exactly one blocker. The mixed P2 report is
  labelled as a mixed blocked report.
- **N1 receipt facts:** the receipt builder emits exactly one `baseline_accepted` fact first, then the
  revision facts in member order and the `shared_definition_changed` facts sorted by part version id;
  the amended contract validation now enforces that order and all tests pass with it.
- **N3 single resolution:** the activation applies the member actions in memory first, then resolves
  the SB-16 baseline once from the resulting project version and reuses that resolution for the
  coordination check, the authoritative readiness recheck, the accepted pins and the pinned snapshot.
- **N4 repository gates:** new `SB-19-repository-gates.txt` with the gate output and the honest
  full-`ci` limitation, plus the matching record check.
