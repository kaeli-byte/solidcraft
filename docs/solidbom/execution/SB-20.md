## Known residual risks

- **Bounded read windows.** The shared-update catalog (500), the project's listed dependencies (200
  with `pending_count` carrying the true total), each dependency's scope targets (500), the flagged
  scenarios (100), the decision history (100) and the global project scan (1000 projects / 200
  returned) are bounded and contract-tested; the truncation paths are not probed at scale. A
  prototype-sized dataset never reaches them.
- **Decision concurrency.** A decision binds the project record version only; it locks the
  engineering and manufacturing heads for consistency but does not expected-version-check them
  (documented amendment). The records are append-only, so no lost update is possible, but a decision
  prepared against an older report could repin a part added by a concurrent engineering/manufacturing
  write in the same project version window. Concurrent editing is out of MVP scope.
- **Global project list cost.** `GET /v2/dependency-projects` resolves each scanned project's
  dependency set in one request, bounded to 1000 scanned projects and the 25 s request bound. That is
  acceptable at MVP scale; a larger deployment wants a per-record reverse index instead of the scan.
- **Aggregate gate coverage.** `cargo xtask ci` was not run in full; see the acceptance gaps.
- **Desktop increment.** The update/adoption surface, controller state and native screenshots remain
  deferred until the SB-10 desktop wiring lands; the package stays `in_progress`.
