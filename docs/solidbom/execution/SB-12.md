## Contract changes and follow-up

Proposed extraction contract (version 1, not coordinator-locked):
`crates/engine/src/solidbom/extraction.rs`

- `ExtractionInput { schema_version, analysis_key, definition_id, category }` with
  `category ∈ {tube, wear_protection, thermal_protection}` from reviewed classification; recognition
  itself remains SB-13's.
- `TubeExtraction { schema_version, analysis_key, extraction_version, definition_id, category, status,
  outer_diameter_mm, inner_diameter_mm, developed_centerline_length_mm, bend_count, bends,
  tangent_straight_lengths_mm, straight_end_lengths_mm, ends, issues }`, all lengths in mm, angles in
  degrees, values as decimal strings per the identity contract.
- `TubeBend { index, centerline_radius_mm, angle_deg, developed_length_mm, start_mm, end_mm }`: `index`
  is the 0-based per-bend identity from the deterministic start end (lexicographically smallest end
  circle center within the extraction tolerance).
- `TubeEndEvidence { end, center_mm, outward_axis, outer_radius_mm, inner_radius_mm }`: end-association
  evidence in the definition frame; radii are the constant wall radii derived from the extracted
  diameters.
- `status ∈ {complete, unsupported}`; unsupported carries no measurements and stable issue codes
  (`open_body`, `mesh_body`, `multiple_bodies`, `unsupported_surface`, `unsupported_face_topology`,
  `unsupported_end_face`, `unsupported_diameter`, `unsupported_split_face`, `ambiguous_centerline`,
  `closed_centerline`, `inconsistent_volume`, `measure_failed`, ...), never display text.
- `TubeExtraction::validate()` checks the versioned shape, non-negative/positive values, bend identity
  order and count, parts adding up, both straight ends, the end-center/tangent-point chain, the
  tangent-to-tangent gaps and each bend's chord. `TubeExtraction::algorithm_is_current()` is the
  algorithm identity a consumer must check together with the whole `AnalysisKey`; the version is
  separate from the key because the manifest extraction the key names does not change with this
  algorithm.
- `extract_definition(session, manifest, input)` validates the request and manifest, refuses a
  stale/foreign manifest, resolves every placement of the definition to one definition body, measures
  that body in its definition frame, and exposes the result. Completion/cancellation: the measurement is
  pure and bounded (one body, ≤ 4096 faces, one exact volume measure), returns complete or explicitly
  unsupported, and has no window-thread or cancellation state; the SMLib exact measure itself is not
  interruptible, so cancellation applies between jobs. Wiring into `AnalysisJob`/`PreparedAnalysis` stays
  with the job owners because that surface is reserved.

No version 1 wire type changes: the existing `Measurement` unit enum has no length unit, so the
extraction contract lives in its own versioned module until a shared length unit is reserved and added.

Known limitations to carry into the lock review:

- Imported bends held only as spline surfaces, a wall split into co-extensive faces along the tube
  (`unsupported_split_face`), corrugated protection, partial/half-shell protection and split end caps
  are reported unsupported; the supported subset is constant-diameter analytic cylinder/torus tubes with
  square annular ends.
- Wear/thermal protection is measured as tubular sleeve geometry; the proposal's "may need distinct
  centerline methods" is not resolved by data yet.
- Customer-reference accuracy/coverage/timing, the zero-reference convention, protection-specific
  centerline methods and the coordinator's contract lock remain open.
- Not every failure branch has a fixture (`inconsistent_volume`, `mesh_body`, the placement-equality
  guard and the co-extensive-split branch are untested); they are defensive refusals, not success paths.
- No production caller beyond the tests yet: the command/job/UI integration is reserved to its owners.
