- **Assignment gate:** integrated SB-14/SB-16/SB-17 are present on the base; the readiness,
  coordination and accepted-baseline contract is locked with its portable types; the shared edits
  are reserved in this record's JSON block. No coordinator-owned ledger, other package record,
  generated file or out-of-scope crate is edited.
- **Service shape:** `services/solidbom-server/src/activation.rs` implements
  `Store::activation_readiness` (read-only), `Store::activate_revisions` (one transaction),
  `Store::accepted_baselines` and `Store::accepted_baseline`, registered behind the four routes in
  `src/api.rs` with the Engineer permission set.
- **Readiness:** resolves the exact current project, engineering, manufacturing and feasibility
  record versions, the registered analyses, the published reference data, the project costing and
  tooling settings and the accepted-baseline head, then evaluates one in-memory SB-16 baseline (the
  same `resolve_baseline` code the costing route uses, appending nothing) and one in-memory tooling
  evaluation. Blockers are typed by owner and scoped exactly as the contract says: product-scoped
  issues block that product, part-scoped issues block members whose resulting costed structure uses
  the part, component/revision-scoped issues block their revision and project-scope issues block
  every member. `no_quoted_products` does not block a quotation-excluded member.
- **Coordination:** the accepted pin set is the contract's semantic
  sourcing/material/dimensions/routing definition of every shared part version used by the costed
  structures of the quotation-included products. Readiness and activation compute the same
  fixed-point closure over the changed pins and the resulting costed structures; an omitted required
  product refuses with `coordinated_activation_required` naming it. Distinct customer revisions are
  distinct part versions, so they stay independent; the activation route cannot mint a revision, so
  an invented revision is an `invalid_request` refusal.
- **Atomic activation:** one transaction: request-id replay, project row lock, expected project
  version and expected accepted-baseline head, identity/activatable checks, recomputed coordination,
  authoritative readiness recheck, the in-memory draft→active/re-pin transitions, one project record
  version, one SB-16 snapshot resolved from that version with no second request receipt, one
  accepted-baseline row naming the pinned project/engineering/manufacturing/feasibility versions and
  the full accepted definition set, and the recorded receipt. Any refusal or failure leaves none of
  them; the domain test injects a failure after the project-version insert by planting a competing
  accepted row and asserts the rollback.
- **Locking:** activation reads the engineering, manufacturing and feasibility record heads with
  `FOR SHARE` after locking the project row, so the versions the readiness gate read are exactly the
  versions the accepted row pins.
- **Increment boundary:** the desktop activation surface and its native evidence are the next
  increment after the SB-10 desktop wiring; the service increment is this delivery.

## Contract changes and follow-up

- The locked contract is consumer-independent for the desktop: it adds
  `ActivationReadinessRequest`/`ActivationReadinessReport` (with `MemberReadiness`,
  `ReadinessBlocker`, `ReadinessOwner`, `CoordinationReport`, `ChangedSharedDefinition`,
  `DefinitionChange`), `ActivateRevisions`/`ActivationReceipt`/`ActivationMember`/`ActivationAction`/
  `PinnedRecordVersions`/`ActivationFact`, `AcceptedBaseline` and its pins/summary/list, and
  `ActivationRefusal`. `API_VERSION` stays 2 and `SCHEMA_VERSION` stays 1.
- Migration `0010_accepted_baselines.sql` adds one append-only table; the stored project,
  engineering, manufacturing and feasibility documents and every earlier table are unchanged, and
  no route updates or deletes an accepted row.
- Behaviour-identical service helper extractions (prep commit `cc5296a3c`): the costing resolution
  and snapshot-insertion split, the reusable project revision-activation transition, the engineering
  issues helper, the current feasibility record reader and the tooling input resolution split. The
  existing suites passed before and after with no answer change.
- **Refusal precedence** is implemented exactly as the locked contract states: malformed envelope and
  unknown product/revision ids (`422 invalid_request`) come first, then `409` in the order stale
  project version, stale accepted baseline, revision not activatable, coordinated activation
  required, member not ready. The readiness route uses the same identity and activatable-revision
  checks.
- **Defensive refusal for an empty accepted state:** `PinnedRecordVersions` validates the record
  versions as at least 1, and a ready activation normally always has an engineering review, a
  manufacturing definition and a feasibility record. A hostile corner with a version 0 record is
  refused with `invalid_request` before anything is written, instead of building a row that fails
  validation; it is a refusal, never a panic and never an invalid stored row.
- The desktop increment (engine commands, controller/client, egui readiness/activation surface,
  native screenshots) remains open and depends on the SB-10 desktop project-record wiring.
