- **Assignment gate:** integrated SB-14/SB-16/SB-17 are present on the base; the readiness,
  coordination and accepted-baseline contract is locked and amended with its portable types; the
  shared edits are reserved in this record's JSON block. No coordinator-owned ledger, other package
  record, generated file or out-of-scope crate is edited.
- **Service shape:** `services/solidbom-server/src/activation.rs` implements
  `Store::activation_readiness` (read-only), `Store::activate_revisions` (one transaction),
  `Store::accepted_baselines` and `Store::accepted_baseline`, registered behind the four routes in
  `src/api.rs` with the Engineer permission set.
- **Readiness:** resolves the exact current project, engineering, manufacturing and feasibility
  record versions, the registered analyses, the published reference data, the project costing and
  tooling settings and the accepted-baseline head, then evaluates one in-memory SB-16 baseline (the
  same `resolve_baseline` code the costing route uses, appending nothing) and one in-memory tooling
  evaluation. Blockers are typed by owner and scoped exactly as the contract says: product-scoped
  issues block that product, part-scoped issues block members whose resulting costed structure uses
  the part, component/revision-scoped issues block their revision and project-scope issues block
  every member. `no_quoted_products` does not block a quotation-excluded member.
- **Coordination (verification fix B1):** the pending changed definitions are computed from the
  accepted-baseline head's whole `shared_definitions` pin set through the contract's
  `pending_shared_definition_changes` helper. While any pin differs, every activation must include
  every quotation-included product whose resulting costed structure uses a changed part, even when
  the request's own members do not use it; an omitted required product refuses with
  `coordinated_activation_required` naming it. The accepted pin set is still recomputed from the
  resulting project version, so a completed activation refreshes it and the pinned snapshot agrees.
  Distinct customer revisions are distinct part versions; the activation cannot mint a revision, so
  an invented revision is an `invalid_request` refusal.
- **Current draft (S2):** only the newest (last) draft revision appended to a product is activatable;
  an older superseded draft is `revision_not_activatable` on readiness and activation.
- **Atomic activation with one resolution (N3):** one transaction: request-id replay, project row
  lock, expected project version and expected accepted-baseline head, identity/activatable checks,
  the member actions applied to the in-memory resulting document, one SB-16 resolution from that
  resulting version (default selections) reused for the coordination check, the authoritative
  readiness recheck, the accepted pins and the pinned snapshot, then one project record version, one
  snapshot row, one accepted-baseline row and the recorded receipt. Any refusal or failure leaves
  none of them; the domain test injects a failure after the project-version insert and asserts the
  rollback.
- **Receipt facts (N1):** exactly one `baseline_accepted` fact first, the revision facts in member
  order and the `shared_definition_changed` facts sorted by part version id, matching the amended
  contract validation.
- **Locking:** activation reads the engineering, manufacturing and feasibility record heads with
  `FOR SHARE` after locking the project row, so the versions the readiness gate read are exactly the
  versions the accepted row pins.
- **Increment boundary:** the desktop activation surface and its native evidence are the next
  increment after the SB-10 desktop wiring; the service increment is this delivery.
